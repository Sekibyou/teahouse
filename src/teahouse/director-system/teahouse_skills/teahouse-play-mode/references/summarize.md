# 总结设计

总结不是"开跑之后再说"的事——它在**构建期**就该被设计好，因为它决定哪些设定以什么结构沉淀，而这些结构正是正文生成要引用的。本文件讲**方法论与构建期职责**；执行 SOP 不在这里。

## 一、产出有且仅有：归档界 + 动态设定

一次总结的产出**只有两样**：

1. **归档界** —— `summary/index.json` 的 `summarized_through`（已总结到第几层）。由后端在 `GitCommit(type="summary", start, end)` 时**自动写入**，导演无需手改。它记录「哪些楼层已被总结覆盖」，作者据此为自己的生成配置挑 `{{glob:runtime/floors/floor-*.md:lastN}}` 的 N——**`lastN` 是写在生成配置里的固定数字，引擎不会替你按归档界裁剪窗口**，这个 N 要靠作者随总结推进自行调准。
2. **动态设定** —— `settings/dyn_settings/` 下的文件。**这是总结的核心产物**：把对后续剧情有持续影响的信息（人物关系、所在地、任务进展、状态变化）沉淀成设定，供正文生成引用。

除此之外的 `summary/sum-*.md` **流水账**只是**导演回溯参考**（深挖设定时用），**不进正文 Bot 上下文**。正文模型不靠总结文本记忆过去，而是靠**设定切片**承载——由生成配置把设定按结构拼进去。

**由此推出构建期的关键结论**：正文 Bot 能记住什么，取决于动态设定的**文件与板块结构**。所以搭设定时就该和总结一起设计——总结往哪个文件、哪个板块写，正文生成就从哪里读。

## 二、谁来执行：实例内的 `summarize-prompt.md`

总结由**总结子会话**执行。它的任务提示词来自**实例文件 `summary/summarize-prompt.md`**（不是 skill）：

```
沙盒「总结归纳」模式
  → readText('summary/summarize-prompt.md')
  → 把 __USER_REQUEST__ 替换为玩家输入的范围
  → sessionCreate({ enabled_tools: [Read/Glob/Grep/GetRuntimeVars/SetRuntimeVar/
      SkillRead/FileOps/Write/Edit/WriteLine/TodoWrite/GitStatus/GitDiff/GitCommit/
      EndSession], reasoning_effort: 'mid' })
  → sessionSend(sid, task) → 子会话执行 → EndSession
```

**所以 SOP 就住在那个实例文件里、允许随实例修改**——每个故事要总结的内容、挂到正文生成的内容都不一样，故它由作者/导演按实例定制。本 skill 不再写第二套 SOP。

## 三、构建期职责：把 `summary/summarize-prompt.md` 建好

搭实例时必须创建这个文件，并写清三件事：

1. **本次总结要维护的动态设定**：列出 `settings/dyn_settings/` 下需要总结时更新的文件（以及每个文件覆盖式更新还是追加）。
2. **本次总结要维护的变量**：列出需要按剧情更新的变量。
3. **要检查的静态切片源**：列出总结时需顺带检查的静态设定（例如某阶段提示词文件是否出现了新档位）。

——也就是说，**这份提示词就是"设定的归位表"在具体实例上的落地**：它规定每类信息在总结时被搬到哪。它应位于**本原型目录下**的 `summary/summarize-prompt.md`。

## 四、结构稳定优先于内容更新（硬约束）

正文 Bot 的上下文靠生成配置里**既有的切片锚点**按结构提取。因此总结时：

- **变量只改值，不增删键**——新增的键没有引用方（用不上），删除键会破坏正文取值。
- **动态设定只改内容，不动结构**——就地更新既有板块/锚点里的内容；不新增/删除板块、不改切片锚点、不重构设定文件与生成配置。
- **确有必要扩结构时先征求同意**——把方案（新建哪个板块 / 锚点放哪个文件 / 为什么正文 Bot 需要它）列给用户过目，获同意才改。

## 五、变量 vs 设定

- **变量**（`runtime/runtime_vars.jsonl`）：高度精炼、会频繁变动的数值/重要值（金币、修为、好感度）。核心变量注入导演系统提示词。**只改既有键的值**。
- **动态设定**（`settings/dyn_settings/`）：较长、中短期生效的**文字状态**（人物关系变化、任务进展、二人闹别扭）。会随剧情变但不是变量，就地维护对应板块/锚点。

判断一段内容落哪一侧的完整归位表见 `references/novel-mode.md` 第六节。

## 六、临时设定：标注生效周期，到期清理

新出现的、非长期状态（一次事件挂起、某个临时悬念、预计会结束的剧情因子），**归入动态设定的既有结构**，不要另起变量、也不要擅自开新模式。

- 用注释语法 `${@note ...}` 标注**生效周期与到期清理提醒**，例如：
  `${@note 临时设定：青云山封印松动，持续到主角取回钥匙（计划 floor-01x 前清理）}`。
  注释正文 Bot 不可见，仅导演 `Read` 时可见并据此周期清理。
- 对**已到生效周期**的临时设定，在总结时**主动清理**——就地删除或改写为已终态，不留失效残留。若清理涉及删除既有板块结构，同样遵循上节"结构稳定"约束。
