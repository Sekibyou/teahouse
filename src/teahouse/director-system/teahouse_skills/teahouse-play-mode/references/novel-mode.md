# 小说模式

小说式的本质：**把设定组织成一条有向无环的引用链（DAG），终点是喂给正文模型的 Generate 配置**。导演的活是维护这条链的**结构与内容**，不是自己写正文。

## 一、引用的形状：一条 DAG

```
settings/static_settings/   ← 长期静态设定（时代/势力/修为分段/背景板），只读引用
settings/dyn_settings/      ← 中短期动态设定（关系/所在地/任务进展），总结产出
        │
        │  二者一起被「组装器」引用
        ▼
settings/assemble.md        ← 组装器（md 中转）：承载全部组织逻辑
        │
        │  yaml 用 {{settings/assemble.md}} 整文件引用它
        ▼
generate-config/*.yaml      ← 薄壳：只写「历史正文 + 用户正文要求」
        │
        ▼
    Generate payload → 正文模型
```

**要点**：正文模型看到的东西，完全由这条链上"被引用到的部分"决定。不在链上的设定 = 正文永远看不到。所以**改设定之前先想清楚它在不在链上**。

**路径基准**：占位符里的文件路径一律**相对实例根目录**（`settings/static_settings/...`，不是 `static_settings/...`）。漏写前缀 = 指向不存在的路径。

## 二、yaml 只当薄壳（YAML 引号坑）

Generate 配置是 YAML 文件。YAML 的引号规则会**先于**占位符解析生效，内嵌引号常在这里二次破坏（`\"` 反斜杠转义在 YAML 里几乎不生效）。所以：

- **最佳实践：不要往 yaml 里写复杂语法**——`${}` 变量、条件切片、`{{}}` 文件引用、内嵌引号，这些全挪进组装器 `.md`；yaml 只留「历史正文 + 用户正文要求」这种纯文本段落，并在 content 里用 `{{settings/assemble.md}}` **整文件引用**组装器。
- 这样 yaml 一处引号都不必写；内嵌引号/花括号/反斜杠全留在非 YAML 的 md 里自然存活。
- 嵌套展开是可行的：Generate 发送前走多轮解析直到稳定，组装器 md 内的 `{{}}` / `${}` 会被后续轮次继续展开。

字段与语法细节见 `teahouse-syntax` skill。

## 三、草稿与转正：不由导演负责

正文的「输出」即**文件落盘**：正文历史唯一来源是 `runtime/floors/`。

- `floor-N-draft.md` —— 半正式稿（创作中，就地覆盖、每层唯一）
- `floor-N.md` —— 正式定稿

**转正由沙盒驱动**：`novel-main.js` **没有**独立的转正确认步骤——转正并入「生成下一章」，它在发现最新章是草稿时**自动**调用 `Teahouse.commitDraft(N)`，后端一次性完成「重算变量 → 冻结快照 → 改名 → git 提交」。

**导演不要自己做 `FileOps move` + `GitCommit` 来转正**。变量也不等转正才生效——**草稿一落盘，后端就重放其变量块，变量随即更新**。

（变量工作值 / 权威快照 / 正式楼层不可变的完整约定，见 `teahouse-sandbox-builder` skill 的 `references/vars-api.md`。）

## 四、手工生成：仅供调试

日常正文由实例里 `novel-main.js` 的生成流水线驱动。**导演手工调 `Generate` 是调试手段**：

- **dry-run（即填 `dump_payload_path`）**：只看最终 payload 组装成什么样（设定切片有没有注入对、条件块命中哪一支）——填了它即写盘并立即返回、不调用模型，这是最常用的自查方式。
- **真实调用**：跑一次看模型产出如何。

需要手工产一篇草稿时，`path` 落 `runtime/floors/floor-N-draft.md`（落盘即在正文历史、触发渲染）。

## 五、正文变量块（teahouse-vars）

正文可携带变量操作，**由正文 AI 在正文末尾就地书写**一个 HTML 注释块。**这个块永远留在正文里**（缓存命中 + 给后续正文 AI 做示范），后端在每次读取变量时重放它。

```html
<!-- teahouse-vars: [
  {"type": "set",   "name": "金币",  "value": 120},
  {"type": "add",   "name": "金币",  "value": -30, "note": "买米"},
  {"type": "append","name": "背包",  "value": {"type": "item", "name": "回血药"}},
  {"type": "pop",   "name": "背包",  "value": {"type": "item", "name": "生锈匕首"}},
  {"type": "x",     "name": "背包",  "index": 2, "value": {"type": "item", "name": "钥匙"}},
  {"type": "set",   "name": "当前状态", "value": "XXX感到不适，皱眉看着主角"}
] -->
```

| `type` | 合法目标 | 语义 |
|---|---|---|
| `set` | boolean/string/number/array | 整体覆盖；name 不存在自动创建 |
| `add` | number | 现值 = 现值 + value；未设按 0 起加 |
| `append` | array | 尾部追加 value |
| `pop` | array | 按值移除第一个匹配 |
| `x` | array | index 处整体替换；index 可负；越界失败 |

- **顺序敏感**：数组从上到下逐条执行；同批按序叠加。
- **块位置**：变量块统一放在正文**最末尾**，且一次输出只用一个块；不要插在正文中间。
- **note 字段**：每条操作可加 `"note"` 极简说明这次变动指代什么剧情（如 `"note": "买米"`），便于回溯；尽量 10 字以内，没有明确指代可省略。
- **类型约束（硬）**：正文 bot 只维护 boolean/string/number/array 四类；**对象不作变量值、不允许 `set`**——对象只能作为数组**元素**出现（配合 `append` / `x`）。
- **强类型与数值边界**：每个变量声明了类型（见变量清单的 `type` 列），`set` 值必须与类型相符；数值变量可有 `min`/`max`，`set`/`add` 写入自动夹取（超界压回边界，正文 AI 按剧情写期望值即可）。
- **解析失败不落痕**：块写坏（JSON 非法、类型不符）时，后端重算会跳过该条，**不改写正文、不写入任何标记**（当前也**没有**把失败说明回传沙盒的通道，出错时由用户侧发现并反馈）。因此改草稿后重算天然幂等。

### 怎么让正文 AI 产出这个块

- 在生成配置（或其引用的组装器）的 **system 段**维护一段「章末用 teahouse-vars 块输出变量操作」的指令（正文 AI 真正读它），并给出上表的 type 语义 + note 说明 + **当前关键变量快照**（名/值/类型）。
- 导演尽量把「要更新的变量」白名单（含类型与边界）帮 bot 建好，减少类型/命名错误。
- 变量清单（正文 AI 需要看到并维护的变量）维护在 `settings/key-vars.md`；实例通常用变量 `启用变量维护` 做开关，由组装器里的条件切片决定整段要不要注入。

## 六、设定与变量的归位

动笔前先想清每段内容该落哪一侧，不要在游玩过程中新建结构：

| # | 内容类别 | 建议位置 | 说明 |
|---|---|---|---|
| 1 | 固定不变设定（正文生成标准、宏观设定） | `settings/static_settings/` | 全剧恒定，只读引用 |
| 2 | 分阶段设定（按变量动态切片） | `settings/static_settings/` | 按变量现值就地选阶段；切片**产物**属动态 |
| 3 | 动态设定模板（如某类型人物模板） | `settings/static_settings/` | 按需**读取模板 → 去 `dyn_settings/` 物化实例**，模板本身不动 |
| 4 | 总结产出的设定 | `settings/dyn_settings/` | 人物关系、所在地、任务进展等 |
| 5 | 游玩中途产生的设定 | `settings/dyn_settings/` | 导演在游玩中即时代落地的新设定 |
| 6 | 随游玩变动的设定（切片产物、模板物化实例） | `settings/dyn_settings/` | 会随剧情变，不是变量 |
| 7 | 变量（数值/重要值的精炼状态） | `runtime/runtime_vars.jsonl` | `SetRuntimeVar`/`GetRuntimeVars`，不放进设定文件 |

**模板 → 实例的模式**：第 3 类放**静态**（框架、可复用的形状），真正的内容在游玩/总结时按需读取模板、到 `settings/dyn_settings/` 内创建实例（对应第 5、6 类）。模板本身长期不动，物化出的实例随剧情演变。

**设定文件的建议格式**：用带明确起止标记的区块（如 `<游戏规则说明>…</游戏规则说明>`），配合切片工具的锚点按区块精确截取。
